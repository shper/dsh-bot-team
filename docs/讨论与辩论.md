# 讨论与辩论

本文说明 **1.3.0 源码版本**中的讨论与辩论能力；源码版本不代表已发布到 npm。安装或更新本地插件目录后，在插件管理中 **disable → enable** 重新加载 Host，再刷新现有 Bot Team 页面；单独刷新浏览器不能替换 Host 模块。版本变更见 [CHANGELOG](<../CHANGELOG.md>)。

本文中的调用示例说明接口契约；实际使用前需查询群与成员，替换示例 ID。

## 选择适合的流程

| 流程 | 参与者与轮数 | 推进方式 | 结束产物 |
|---|---|---|---|
| 结构化讨论 `structured` | 至少 2 位发言成员；默认 3 轮，允许 2–20 轮；界面提供快速 2 / 标准 3 / 深入 5 轮 | 观点 → 中间轮质询 → 最后一轮收敛，每个非末轮后有小结 | 可选最终总结，整理共识、分歧、待决事项 |
| 经典讨论 `classic` | 至少 1 位成员；默认 2 轮，1–20 轮 | 按所选成员顺序逐轮自由发言 | 可选最终总结；没有结构化轮间小结 |
| 1v1 辩论 `debate` | 正反方各 1 人，必须是不同 Bot；可另选独立裁判；问答默认 2 轮，1–20 轮 | 双方开篇 → 交叉问答 → 双方总结陈词 → 可选裁决 | 有裁判时给出裁决；没有裁判时不生成胜负 |

界面新建表单默认使用结构化讨论、3 轮并启用最终总结。已有 `bot_team_discuss` 调用保留 `classic` 默认 2 轮、默认总结的语义。直接调用 HTTP action 的 classic 模式仍保留原有的 `summarize:false` 默认值；需要总结时应显式设置。

同一群只允许一个未结束的讨论或辩论。`running / pausing / paused / finalizing / stopping` 都占用该位置；只有 `done / stopped` 是终态。单聊不支持这些流程。

## 在界面中使用

1. 进入群聊，确认所需 Bot 已加入并启用，然后点击群头部的**讨论/辩论**。
2. 选择**多成员讨论**或 **1v1 辩论**，填写议题。多成员讨论可勾选参与者并调整发言顺序；辩论分别指定正方、反方、立场和可选裁判。
3. 选择快捷轮数，或选择**自定义…**后输入整数：结构化讨论 2–20 轮，经典讨论和辩论 1–20 轮。预计发言次数会随之更新；切换讨论与辩论会保留各自的轮数设置。讨论的**小结与总结成员**默认取第一位参与者，也可以另选本群其他成员，单独负责小结和总结；该角色可以与发言者兼任。辩论裁判必须独立于双方。
4. 按需打开**高级设置**，填写目标、背景、讨论成员视角、发言长度和输出语言。引用材料可以填写本群消息 ID，也可从已加载消息中勾选；支持本群历史会话的消息。
5. 开始后在**右侧成员列表下方**查看阶段、当前发言者、轮次和状态，并使用暂停、继续、重试、提前结束、停止或补充材料。状态区仅在当前会话有未结束的讨论或辩论时显示；普通聊天、已完成或已停止的流程不显示。右栏收起或窄屏隐藏时，可从顶部**查看当前讨论**或**查看当前辩论**打开对应详情并操作；结束后的完整记录仍可从消息的**讨论详情**或**辩论详情**进入。讨论和辩论分别显示自己的消息类型、配置标题、进度和操作文案。

也可以右键群聊中的消息，选择**发起讨论**或**发起辩论**，直接打开对应配置。议题会预填消息文本（最多 2000 字符），完整原消息会自动加入引用材料；本群历史会话中的消息也可引用到当前会话。确认配置后点击**开始讨论**或**开始辩论**才会启动。消息仍在生成、没有文本或当前已有未结束的讨论/辩论时，这两个菜单项不可用；单聊不显示这两个选项。

若本地插件的前端已更新，而 DSH 仍运行旧版 Host，详情接口可能返回 `未知操作: discussion.get`。此时详情会兼容读取群内已保存的讨论消息与总结，保留刷新和跳转原文；仅在明确不支持该操作时启用兼容读取，不会掩盖权限、记录不存在或服务错误。完整详情接口需重新加载更新后的 Host（必要时完全退出并重新启动 DSH），仅刷新页面不会更新后端。

结构化讨论即使关闭**结束后生成最终总结**，非末轮之后的 `checkpoint` 小结仍会执行。小结与最终总结是不同步骤。

一次逻辑步骤可能包含多次原生模型轮次、工具调用或目标续跑。界面预计的发言次数是计划中的逻辑步骤数，实际模型调用次数和 Token 消耗可能更多。例如，2 人、3 轮、带最终总结的结构化讨论有 9 个计划步骤；默认 2 轮且带裁判的辩论有 13 个。

## 阶段如何推进

### 结构化讨论

| 阶段 | 标识 | 行为 |
|---|---|---|
| 第一轮观点 | `viewpoint` | 每位发言者依次给出立场、依据和假设 |
| 中间轮质询 | `challenge` | 围绕前文提出疑问、反例和需要补证的地方 |
| 最后一轮收敛 | `converge` | 根据已有讨论调整观点、提出可执行结论或仍待解决的问题 |
| 轮间小结 | `checkpoint` | 小结成员在每个非末轮之后整理进展，供后续步骤参考 |
| 最终总结 | `summary` | 启用 `summarize` 时，由总结成员单独生成最终结果 |

2 轮的快速模式只有观点轮和收敛轮，中间没有质询轮；3 轮有 1 个质询轮，5 轮有 3 个。参与者顺序用于每个发言轮，小结不会改变该顺序。

经典讨论使用 `discussion` 阶段逐轮发言，按配置追加 `summary`，保留原有轮次含义。

### 1v1 辩论

双方先各执行一次 `opening`。每轮交叉问答包含双方各一次 `question` 和一次 `answer`：

| 问答轮 | 先后顺序 |
|---|---|
| 奇数轮（第 1、3、5…轮） | 正方提问 → 反方回答 → 反方提问 → 正方回答 |
| 偶数轮（第 2、4、6…轮） | 反方提问 → 正方回答 → 正方提问 → 反方回答 |

问答结束后，正反方分别执行 `closing` 总结陈词。有裁判才会追加 `judgement`，无需另设讨论总结开关。裁决值为 `pro / con / tie / insufficient`：

- `pro`：正方占优；`con`：反方占优。
- `tie`：双方证据充分，但未形成胜负差异。
- `insufficient`：证据不足以判断。裁判必须依据实际完成的双方内容；没有足够的双方证据时只能返回此值，不能凭角色或缺席默认判胜。

没有裁判时，流程保留双方发言与总结陈词，不生成 `verdict`，也不把辩论包装成双方共识。

## 运行中控制

| 操作 | 含义与边界 |
|---|---|
| `get` | 读取当前快照和 transcript；可查看同群历史讨论，不恢复或推进历史执行 |
| `pause` | 不再派发下一步骤；当前逻辑步骤完成后从 `pausing` 转为 `paused`。不会为了暂停而把仍在执行的步骤直接当作完成 |
| `resume` | 从暂停处继续。存在失败步骤时返回 `retry-required`，不会跳过失败并进入下一步 |
| `retry` | 重试失败的同一逻辑步骤，创建新 attempt；之前的尝试与消息保留，便于核查 |
| `finish` | 提前收束：当前执行结束后跳过未完成的普通讨论/问答，保留配置中的最终总结，或辩论总结陈词与裁决。结果以 `partial:true` 标记为提前结束，证据不足时不能强判胜负 |
| `stop` | 关闭后续派发并请求停止当前执行，不新建总结或裁决；已产生的内容保留。原生执行仍忙或状态不明时保留 `stopping` |
| `add_context` | 补充用户指导或引用材料；从下一次执行开始生效，也适用于后续 retry，不改写已经提交给模型的提示或已完成的历史 |

`add_context` 至少需要非空 `text` 或有效 `contextMessageIds`。每次引用最多 20 条，必须属于本群，可以来自历史会话；接纳时捕获引用快照，不自动带入整段历史，不接受其他群的消息。后续修改或删除来源消息不会把已捕获的材料替换成另一条消息。

暂停不是停止：`paused` 仍阻止新讨论/辩论、`/new` 和项目目录切换。若只是等待提问、审批或目标续跑，需先处理该原生执行；暂停要等待整个逻辑步骤结束。

停止也可能需要收尾。`stopping` 表示停止请求已经接纳，但不能确认原生作业、目标、子代理或待执行输入均已空闲。可先 `get` 检查状态与原因，处理剩余工作后再发**新的** `stop` 请求重新检查。不要把同一个 `requestId` 的幂等重传当作新的停止检查。

## 模型工具

普通会话可以调用这些工具；群内 Bot 禁用发起与控制类工具以防递归，只读列表仍可使用。当前工作区合计 10 个工具，新增的是 `bot_team_debate` 和 `bot_team_discussion_control`。

先用 `bot_team_list` 查群、成员名字和当前会话；带 `groupId` 与 `includeMessages:true` 时，近期消息包含可引用的 `messageId`。下面的群名、成员名和 ID 均为示例，实际调用需替换为查询结果。

### 启动讨论：`bot_team_discuss`

| 字段 | 说明 |
|---|---|
| `groupId / topic` | 必填；议题最多 2000 字符 |
| `members` | 参与 Bot 名字数组，顺序即发言顺序；省略时选所有可用成员；空数组无效 |
| `format / rounds` | `classic` 默认 2 轮，范围 1–20；`structured` 默认 3 轮，范围 2–20，至少 2 人 |
| `summarize` | 是否执行最终总结；工具默认 `true` |
| `summaryMember` | 小结与总结 Bot 名字，默认第一位参与者；可另选本群成员 |
| `perspectives` | 成员名字到视角文本的映射，每段最多 500 字符；仅限本次参与者或指定总结成员 |
| `goal / background` | 可选目标与背景，分别最多 2000 / 12000 字符 |
| `responseLength` | `short / standard / detailed`，默认 `standard`；是提示偏好，不是硬性字数上限 |
| `language` | `auto / zh / en`，默认 `auto`；控制生成语言，不翻译已有发言 |
| `contextMessageIds` | 可选本群显式引用，最多 20 条；支持历史会话消息 |
| `wait / timeoutMs` | 默认等待到暂停或结束；等待预算来自 `config.toolWaitTimeoutMs`，可用 `timeoutMs` 覆盖 |

调用 `bot_team_discuss`：

```json
{
  "groupId": "grp_demo",
  "topic": "下一版应优先优化响应延迟还是降低成本？",
  "format": "structured",
  "members": ["Alpha", "Beta"],
  "rounds": 3,
  "summarize": true,
  "summaryMember": "Reviewer",
  "goal": "给出有条件的推荐方案和待验证指标",
  "background": "团队只能安排一个迭代，需兼顾稳定性。",
  "perspectives": {
    "Alpha": "关注用户体验与响应延迟",
    "Beta": "关注维护成本与失败风险"
  },
  "responseLength": "standard",
  "language": "zh",
  "contextMessageIds": ["msg_evidence"],
  "wait": false
}
```

名字匹配接受 `@Name` 和大小写归一化。未知名字、同名歧义、重复参与者或停用成员会明确报错，不会静默丢弃。若只需要兼容旧流程，省略 `format`，例如 `{ "groupId": "grp_demo", "topic": "设计评估" }`，仍为 classic 2 轮。

### 启动辩论：`bot_team_debate`

必填 `groupId / topic / pro / con`；`pro / con / judge` 使用名字。`judge` 可选，必须不同于双方；`proPosition / conPosition` 可选，每段最多 2000 字符。`rounds` 默认 2，严格为 1–20 的整数。目标、背景、长度、语言、引用及等待字段与讨论工具相同；此工具不接收 `members / format / summarize / perspectives`。

调用 `bot_team_debate`：

```json
{
  "groupId": "grp_demo",
  "topic": "下一版是否应立即切换缓存方案？",
  "pro": "Alpha",
  "con": "Beta",
  "judge": "Reviewer",
  "proPosition": "支持立即切换，但给出回滚条件",
  "conPosition": "主张先完成指标验证再切换",
  "rounds": 2,
  "goal": "依据可验证证据比较两种路径",
  "responseLength": "standard",
  "language": "zh",
  "wait": false
}
```

省略 `judge` 即无裁判模式；不要把没有 `verdict` 解释为 `tie`。

### 查看与控制：`bot_team_discussion_control`

必填 `discussionId / operation`。`operation` 是上表中的 `get / pause / resume / retry / finish / stop / add_context`。其他可选字段为 `text / contextMessageIds / expectedRevision / requestId / wait / timeoutMs`。工具会从记录读取所属群，并自动使用该群当前 `expectedConversationId`，无需用户填写群 ID 或会话 ID。

调用 `bot_team_discussion_control` 读取状态：

```json
{
  "discussionId": "discussion_demo",
  "operation": "get"
}
```

再使用实际返回的 `revision` 补充材料；示例中的 12 必须替换为当前值：

```json
{
  "discussionId": "discussion_demo",
  "operation": "add_context",
  "text": "请补充评估回滚需要的时间与数据兼容成本。",
  "contextMessageIds": ["msg_followup"],
  "expectedRevision": 12,
  "requestId": "demo-add-context-1",
  "wait": false
}
```

`get` 默认立即返回，只有显式 `wait:true` 才等待。其他控制默认等待，`wait:false` 立即返回当前快照。等待达到预算只结束这次工具等待，不停止后台流程；可以稍后再次 `get`。

工具输出保留 `discussion / transcript / summary`，有有效裁决时增加 `verdict`。`discussion` 包含阶段 `stage/phase`、`side`、`revision`、`currentStepId/currentStep`、`currentSpeaker`、`status`、`reason`、`awaitingUser`、`partial` 和 `settled`；`partial` 明确表示提前收尾。`paused` 会让等待返回，但 `settled:false`；v2 仅 `done/stopped` 为 `settled:true`，`wait:false` 不会假定流程完成。

工具 transcript 保留 Bot 发言，并带 `messageId / groupId / conversationId / discussionId / stepId / phase / side`，按记录的群、会话、讨论 ID 精确过滤，文本可能截断。`summary` 取已接受的最终结果，不将失败或未接受的草稿作为结论。完整原始消息可通过下面的 action 获取。

## HTTP action 接口

通过已登录的 DSH 会话调用 `POST /api/bot-team.action`，请求体为 `{ "action": "…", "payload": { … } }`。没有登录态的请求返回 401。Host 内部对应 `service.dispatch(action, payload)`，读写都经过所属群的操作保护。

| action | 作用与返回 |
|---|---|
| `discussion.start` | 启动讨论或辩论，返回新 discussion 记录；不等待模型完成 |
| `discussion.get` | 只读查询，返回 `{ discussion, transcript, summary?, verdict?, missingMessageIds }`；transcript 是原始消息数组，允许查看历史会话中的记录 |
| `discussion.control` | 执行控制，返回最新 discussion；operation 不包含 get，读取请使用独立的 `discussion.get` |

HTTP 成功响应统一为 `{ "ok": true, "result": … }`。模型工具的 `wait / timeoutMs` 是工具层等待选项，不是这些 action 的阻塞参数。订阅 `GET /api/bot-team.events?groupId=…` 或再次查询可以获取后续状态。

模型工具以名字选人，service/action 以成员 ID 选人：

| 模型工具字段 | service/action 字段 |
|---|---|
| `members` | `membershipIds` |
| `summaryMember` | `summaryMembershipId` |
| `pro / con / judge` | `proMembershipId / conMembershipId / judgeMembershipId` |
| `perspectives` 的名字键 | `perspectives` 的 membership ID 键 |

其他配置字段同名。`mode` 为 `discussion / debate`，省略时为 discussion；`format` 用于讨论的 classic/structured。HTTP structured 默认 3 轮并启用总结；HTTP classic 默认 2 轮且默认不总结。辩论只根据是否设置裁判决定是否计划 `judgement`。

启动结构化讨论的请求体：

```json
{
  "action": "discussion.start",
  "payload": {
    "groupId": "grp_demo",
    "expectedConversationId": "conversation_current",
    "mode": "discussion",
    "format": "structured",
    "topic": "比较缓存方案的收益与迁移风险",
    "membershipIds": ["mem_alpha", "mem_beta"],
    "summaryMembershipId": "mem_reviewer",
    "rounds": 3,
    "summarize": true,
    "perspectives": {
      "mem_alpha": "性能收益",
      "mem_beta": "迁移与维护成本"
    },
    "language": "zh"
  }
}
```

查询请求体；指定 `groupId` 时，必须与该 discussion 所属群一致：

```json
{
  "action": "discussion.get",
  "payload": {
    "groupId": "grp_demo",
    "discussionId": "discussion_demo"
  }
}
```

控制请求体；使用刚查询到的 revision 和该群当前会话 ID：

```json
{
  "action": "discussion.control",
  "payload": {
    "groupId": "grp_demo",
    "discussionId": "discussion_demo",
    "expectedConversationId": "conversation_current",
    "operation": "pause",
    "expectedRevision": 12,
    "requestId": "demo-pause-1"
  }
}
```

并发与幂等字段分别解决不同问题：

- `expectedConversationId`：外部 start/control 必填，表示提交者看到的当前会话。缺失时返回 `reload-required`；已切段时返回 `stale-conversation`。历史 discussion 可 get，不可控制；即使填当前会话 ID，也不能把历史记录重新激活。
- `expectedRevision`：控制的可选非负整数前置条件。不匹配时返回 `stale-revision`，应重新 get，检查新状态后决定操作，不能盲目覆写。
- `requestId`：控制请求的可选幂等标识，非空且最多 160 字符。同一请求因网络问题重传时复用该值，返回当前记录而不重复生效；不同操作、新意图或再次停止检查必须使用新值。启动请求的 `requestId` 在当前群的当前会话中单独去重；重传会返回原活动，改变议题或配置时应使用新值。

新记录使用 `protocolVersion: 2`，保存 `mode / format / steps / currentStepId / currentSpeaker / phase / revision / status`。每个 step 有 `stepId / phase / membershipId / side / round / status / attempts / messageIds`；retry 增加 attempt，不伪装成新讨论。一个 attempt 可关联多条原生回复，不能把每条流式或续跑消息当作新的逻辑步骤。

## 恢复与已知边界

- 存储 schema 升至 **v8**。旧讨论保留 classic 轮次、成员顺序与原消息，不从旧 transcript 推造缺失的步骤或尝试日志；它们不自动变为 structured 或 debate。
- 崩溃或重新加载 Host 后，未结束的 v2 流程先进入 `paused`，不会静默重跑。恢复控制会先检查参与者的原生 session、作业、目标、子代理和输入队列，再核对已持久化步骤；失败步骤需 retry，不能靠 resume 跳过。
- 先前已请求 stop 的恢复记录必须完成停止，不能通过 resume 复活。原生忙或状态未知时维持保护；停止后是否能 `/new` 或切换项目，仍以重新检查结果为准。
- `paused` 不是终态，不释放同群讨论位置，也不允许通过新建流程绕过未完成工作。成员移除、停用或底层 Bot 不可用可能暂停后续步骤，需要处理原因或选择收束/停止。
- 角色、立场、视角都是本次执行的临时提示，**仍复用成员的原 session**。裁判使用独立成员并不保证没有历史记忆；本实现不提供角色隔离会话或对立立场间的记忆隔离。
- 补充材料是显式用户输入，从下一次执行（含 retry）生效。引用仅限同群，并捕获被选消息快照；不会隐式读取其他群或整段旧会话。
- 删除原始消息后，`discussion.get` 可通过 `missingMessageIds` 报告缺失来源；已接受并保存的最终总结仍可读取。查看 transcript 不会补造被删除的原文。
- 提前结束、模型失败、成员不可用或材料不足都可能使结论不完整；有裁判也不能将缺失证据当作对方落败。无裁判模式始终不输出胜负。
- 工具的等待预算、单轮执行时限与每日 Token 预算是独立设置。等待返回或超时不代表已停止原生执行；实际工具、文件与审批权限继续遵守群工作目录和宿主策略。

## 维护验证

从仓库根目录运行 `npm run check` 与 `npm test`。涉及原生执行收尾或恢复时，另按[后台会话与完整日志](<原生会话与完整日志.md#验证与加载>)运行安装版宿主契约测试。

界面回归应覆盖结构化/经典讨论、带裁判及无裁判辩论、自定义轮数、暂停/恢复/重试/停止、历史详情与旧 Host 兼容读取，并检查 zh/en、深浅色与窄屏。部署验收需重新加载 Host 后在现有 GUI 中进行；以本次结果记录通过项与未验证项。
