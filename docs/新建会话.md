# 新建会话 `/new`

本文记录当前实现的数据与恢复契约，供维护会话切换、历史日志和执行隔离时使用。操作方式与草稿行为见[使用指南](<使用指南.md#在当前聊天开始新会话-new>)，后台 Agent 的能力和忙状态边界见[后台会话与完整日志](<原生会话与完整日志.md>)。这些说明不代表工作区改动已经发布。

## 行为范围

完整输入 `/new`，或使用输入框 **+ → 指令 → 新建会话**、顶部 **··· → 新建会话**，会在当前聊天开始新的逻辑会话。单聊只影响当前 Bot；群聊同时切换全部成员，包括停用成员。

聊天身份、成员、人格与模型设置、工作目录、项目文件、附件、历史消息和日志保留。新段不自动带入旧聊天、执行历史、压缩摘要、目标或任务。明确回复或引用旧消息时，只带入用户选中的消息快照。新建本身不调用模型、不重置每日预算，也不预先创建每个成员的 Agent。

## 数据模型与不变量

数据分三层：聊天（group）持有当前逻辑会话指针；逻辑会话（Conversation）保存消息边界；成员在需要执行或准备 Skill 时建立底层 DSH session。同一段内因项目目录或 preset 变化可以轮换多个 session，连续未使用的空段可以没有任何底层 session。

| 记录 | 关键字段与用途 |
|---|---|
| group | `activeConversationId` 是当前执行会话的唯一权威；`conversationVersion` 单调递增 |
| conversation | `conversationId / groupId / ordinal / previousConversationId / afterSeq / requestId`，不可变的历史链与幂等结果 |
| member | `sessionConversationId` 标记保存的 `sessionId` 属于哪段；`lastSeenSeq` 是该成员的消息游标 |
| session binding | 记录 `sessionId / groupId / conversationId / membershipId` 及 Bot 快照，独立于成员和消息的生命周期 |
| message、job、task、discussion、interaction | 固定 `conversationId`，供执行、异步回调与历史动作校验 |

维护时必须保持：

- 只有从 `group.activeConversationId` 沿历史链可达的 Conversation 才算已提交；准备记录不能出现在普通查询中。
- `afterSeq` 来自单调的 `group.nextSeq`。例如 `afterSeq: 180` 只允许自动带入 `seq > 180` 的消息；删除消息不能把边界倒退。
- 普通增量上下文下界为 `max(member.lastSeenSeq, conversation.afterSeq)`；新 session 回填的下界为 `conversation.afterSeq`。加入成员、恢复、目录/preset 变化及任务/讨论等路径使用相同边界。
- 同一底层 session 只归属一段 Conversation；换 session 不一定换逻辑会话。绑定写入后仍需按实际日志是否存在显示 availability。
- 当前执行资格与历史日志所有权分别校验。旧日志可查看，但不能因此恢复旧 Agent 或继续旧任务。
- 每个 job 和回调核对当前会话、成员和实际 session；迟到事件不能产生新段回复、覆盖新映射或推进新段任务。

核心实现位于 [domain.js](<../host/domain.js>)、[conversations.js](<../host/conversations.js>)、[service.js](<../host/service.js>) 与 [agents.js](<../host/agents.js>)。

## 提交、幂等与失败恢复

宿主存储没有跨表事务；实现依赖单 Host 写入、群级操作保护和严格持久化。切换顺序为：

1. 校验 `groupId / expectedConversationId / requestId`，优先返回已提交的同请求结果。
2. 同步取得群级切换保护，阻止新的输入、派发、Agent/Skill 准备及冲突设置变更。
3. 检查当前指针及插件、原生活动；等待已经接纳的相关写入完成，再检查一次。
4. 严格释放插件拥有的旧 Agent handle；等待后代收尾，重新检查活动并等待持久写入完成。
5. 写入新的不可变 Conversation，再把 `group.activeConversationId` 与 `conversationVersion` 写盘。组记录写入成功是唯一提交点，随后才发布内存状态。
6. 提交后发送 `conversation.started` 并返回权威状态；各成员首次需要 Agent 时才分配新 session。

| 失败位置 | 恢复规则 |
|---|---|
| 繁忙、冲突、写入或释放失败 | 不提交新指针；已释放成员仍可按旧映射恢复 |
| 准备记录已保存，指针尚未保存 | 未被当前历史链引用的记录不可见；继续旧段 |
| 指针已保存，响应或 SSE 丢失 | 新段有效；同 `requestId` 重试返回原结果，不再切换 |
| 新段首次创建 Agent 失败 | 新段仍有效，可重试创建，不能回退到旧 session |

同一 `requestId` 必须对应同一聊天和预期父会话；冲突返回错误。重放早先成功的请求会同时返回那次创建记录与现在的当前会话，客户端不能因此倒退指针。新的用户意图使用新 `requestId`；连续新建空段仍保留不同 ordinal。

严格写入须先等待后端成功，再替换内存 Map；异步写回重新读取最新记录，不能用旧 group/member 对象覆盖新会话字段。

## 忙状态与执行隔离

运行/排队中的回复、未结束的讨论或辩论、Agent/Skill 准备、设置变更、提问/审批及正在提交的回答都可能阻塞切换。还需检查当前与历史绑定 session 的原生 Agent、inbox、已授权续跑的 goal、Job 和后代。只剩持久化的已接纳输入先排空写链，不能在它写完前提交新边界。

Agent 为 idle、停止按钮已返回或子代理目录写着 inactive 都不足以证明工作结束。Job 仅 `completed / failed / killed` 是终态；插件只释放自己拥有的 handle，不能替其他所有者销毁借用的 Agent。当前 SDK 无法可靠证明 external/unknown 后代终态，查询失败或缺少必要能力时拒绝切换。停止或重启不保证解除这种阻塞，细节见[原生活动边界](<原生会话与完整日志.md#为什么停止后仍可能无法新建>)。

旧任务、评审/修改、重试和讨论保留为历史；不能直接继续旧执行链或自动解锁派发到新段。显式引用由 Host 校验同群来源并保存正文、作者、附件等快照；不会补入周围历史，也不把引用内容解释为管理命令。

## HTTP 与同步

通过认证的 `POST /api/bot-team.action` 新建：

```json
{
  "action": "conversation.new",
  "payload": {
    "groupId": "grp_example",
    "expectedConversationId": "conv_current",
    "requestId": "request_example"
  }
}
```

`requestId` 使用 1–160 位字母、数字、下划线或连字符。成功响应的 `result` 包含 `created`、本次 `conversation`、`currentConversationId` 与 `conversationVersion`。同请求重放时 `created: false`。

| 通道 | 契约 |
|---|---|
| `bootstrap` | 下发 capability、当前会话与版本、可切换状态及 blockers |
| `messages` | 保留全聊天消息分页，附会话边界；边界不计入消息分页 limit |
| `conversations` | 按 `groupId / beforeOrdinal / limit` 查询已提交历史；指定 `conversationId` 读取会话及 session 归属 |
| `events` | 提交后发 `conversation.started`；重连 hello 与 GET 恢复权威状态 |
| 执行过程、历史日志、JSONL 导出 | 校验可信历史归属，只读查询，不创建或恢复 Agent |

外部执行请求需要 `expectedConversationId`；缺失返回 `reload-required`，已过期返回 `stale-conversation`，不会静默送进新段。内部工具在受保护入口取得并固定当前 ID，历史目标仍需单独拒绝。`message.post` 收到完整 `/new` 返回 `command-required`，要求使用管理 action；普通正文、代码、引用或模型输出不会触发切换。

| HTTP 状态 | 主要错误 |
|---|---|
| 400 | `invalid-input`、`invalid-command`、`command-required` |
| 404 | 新建请求的聊天不存在 |
| 409 | `conversation-busy`、`stale-conversation`、`historical-target`、`reload-required`、`conflict` |
| 500 | `storage-failed`、`session-release-failed`、`conversation-corrupt` |
| 503 | `conversation-capability-unavailable` |

错误结构为 `{ ok: false, error: { code, message }, details: ... }`，`details` 在顶层，包含可用的当前状态或阻塞原因。

Client 从 action、GET、bootstrap 和 SSE 合并状态时，只接受不低于已知 `conversationVersion` 的当前指针；同版本不同 ID 需重新查询。旧响应可补历史消息，但不能覆盖新指针。非空跨窗口草稿保持原归属，用户明确采用后再发送；409 不自动重发。

## 历史展示与迁移

时间线分隔来自 Conversation 元数据，按 `afterSeq / ordinal` 排序并以 ID 去重；它不占消息 seq、未读或 Token 计数，也没有普通消息删除动作。连续空段和删除完消息的历史段仍保留边界。已打开的执行面板与日志固定原 session，新建不会改向。

会话模型由 schema 7 引入，当前整体存储 schema 为 8。升级为每个旧聊天建立稳定基线，保留 session、消息与游标，不因升级清空记忆；历史绑定来自成员映射和可信执行引用，不能猜测归属。迁移须先完成各群持久提交，才标记 schema 成功并允许恢复执行。

启动时校验指针存在、群归属、版本、历史链无环和边界单调；错误时停止相关执行，不能回退到 seq 0。格式变更前应停插件并备份存储；旧版不理解新上下文边界，不能直接降级后继续写入新格式数据。
