## 1. 数据模型与状态机

### 1.1 `tasks` 表（domain `bot_team`，schema v3）

```ts
interface Task {
  taskId: string;            // 'task-<uuid>'
  groupId: string;
  title: string;
  description: string;
  acceptance: string;        // 验收标准（用于评审提示词）
  assigneeMembershipId: string;
  reviewerMembershipId?: string;
  status: 'pending' | 'in_progress' | 'delivered' | 'changes_requested' | 'accepted' | 'cancelled';
  deliverableMessageId?: string;   // 交付物消息
  reviewMessageId?: string;        // 评审请求消息
  reviewReplyMessageId?: string;   // 评审回复消息（修改 prompt 使用）
  revision: number;                // 交付/评审轮次
  lastError?: string;
  createdAt: number; updatedAt: number;
}
```

### 1.2 状态流转

```
pending ──派发──▶ in_progress ──Bot交付──▶ delivered
                                          ├──请评审(reviewer) ──verdict=pass──▶ accepted
                                          │                    └verdict=需修改──▶ changes_requested
                                          ├──验收通过(人工)──▶ accepted
                                          └──要求修改(人工)──▶ changes_requested
changes_requested ──让作者修改──▶ in_progress ──交付──▶ delivered
任意非 accepted ──取消──▶ cancelled
```

- 交付/修改 turn 的占位消息带 `meta.taskId`，引擎在 `turn/end` 后把 `deliverableMessageId` 回填任务；
- 评审 turn 也带 `meta.taskId`，评审完成后按 `verdict` 自动把任务流转为 `accepted` / `changes_requested`；
- 所有流转持久化并广播 `task.updated`（SSE），UI 实时更新。

## 2. Engine / Prompt

- 新增 job kind：`task`（派发交付）、`task_revision`（按意见重新交付）；均走既有占位消息、并行上限、超时、取消与配额逻辑。
- 任务 prompt（`buildTaskPrompt`）：任务标题/描述/验收标准 + 最近上下文 + 「只输出交付内容」。
- 修改 prompt（`buildTaskRevisionPrompt`）：原交付 + 修改意见（评审回复）+ 验收标准 + 「输出完整修改版」。
- Engine 增加 `taskHook(job, message, status)`：任务交付回填、评审 verdict 流转；失败时记录 `lastError` 并回到 `in_progress` 以便重派。

## 4. 验证

### 4.1 自动冒烟 `smoke-v7`（16/16）

```json
{"pass":true,"detail":{"step":"smoke-v7","checks":{
  "mentionReply":true,"noMentionNoReply":true,"parallelReplies":true,
  "personaFilePersisted":true,"personaInSystemPrompt":true,
  "reviewVerdict":true,"authorRevision":true,"discussionRounds":true,
  "modelToolsRegistered":true,"schemaVersionMigrated":true,
  "sandboxTierReadOnly":true,"quotaWithinLimits":true,"quotaRejectsOverLimit":true,
  "healthEndpointShape":true,
  "taskFlowAccepted":true,"taskChangesAndRework":true},
  "tasks":{
    "taskA":{"status":"accepted","revision":2,"deliverable":true},
    "taskB":{"finalStatus":"accepted","deliverable":true,"revision":2}}}}
```

- **Flow A（模型 verdict 链路）**：创建任务（验收含 `TASK-A-OK`）→ 派发 → Bot 交付 → 请 B 评审 → verdict=`pass` → 任务 `accepted`。
- **Flow B（返工链路）**：创建任务 → 派发 → 交付 → 人工「要求修改」→ `changes_requested` →「让作者修改」→ 重新交付 → 人工验收 → `accepted`。
  > 说明：Flow B 故意使用人工要求修改，避免让冒烟依赖 LLM 一定输出「需修改」；模型 verdict 的「需修改」路径在 M2 评审控件中已覆盖，两处互补。

### 4.2 真实数据（domain）

```
TASK A: deliverable #145 "TASK-A-OK"  review #147 verdict=pass  → accepted, revision=2
TASK B: deliverable #149 "TASK-B-OK 12345"（模型按验收标准补齐）→ changes_requested → 修改 → delivered → accepted, revision=2
```

## 5. 本次修复的验证问题

| # | 问题 | 根因 | 处理 |
|---|---|---|---|
| S1 | 首次 task smoke 的 Flow B 依赖评审者按验收标准输出「需修改」，但模型输出「通过」，导致任务被自动 accepted，`task.revise` 报“只有被要求修改的任务可以重新交付” | 用 LLM 判决做状态机断言不稳定 | Flow B 改为确定性的「人工要求修改 → 修改 → 交付 → 人工验收」；模型 verdict 路径由 Flow A 覆盖。另外清理了失败轮次留下的重复任务 |

## 6. 已知限制 / 后续

- 任务**模型工具**尚未暴露（当前任务操作为 UI + HTTP action；模型工具已有 group/review/discussion，可后续增加 `bot_team_task_*`）。
- 任务编辑/删除 UI 未做；错误后可重新派发/取消，但不能改标题/验收标准。
- 评审 verdict=pass 会自动 `accepted`；人工仍可在 delivered 状态覆盖（验收/要求修改）。
- 无排期/优先级/依赖/工作量，v2 视需要扩展。
- 完整 i18n、按 capability 精确收敛工具可见性仍为后续项。
